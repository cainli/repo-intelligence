# repo-intelligence vs codebase-memory 对比评测报告

- **日期**:2026-08-28
- **被测**:repo-intelligence v0.1.36(release 构建)vs codebase-memory MCP(会话内当前版本)
- **主目标项目**:验证项目/ruoyi-vue-plus(6.X 分支,head `41ea764a`,701 个 Java 文件,315MB)
- **副目标**:repo-intelligence 自身(Rust,用于反向测 cb 语言覆盖)
- **方法**:同机、同项目、同一问题集双侧执行;响应字节数 / 往返次数 / 结果正确性为主,
  RI 侧可精确计时(CLI/sqlite3),cb 侧无计时段的部分标注为定性观察

## 0. 一页结论

| 维度 | 权重 | RI | cb | 胜方 |
|---|---|---|---|---|
| A 索引效率 | 15% | **8.5** | 7 | RI(10.86s 全量 / 0.60s 无变化重扫,全程可观测;cb 无计时段) |
| B 查询效率 | 15% | **8** | 6 | RI(SQL 直查 1 步到位;cb 需 2-3 步链式定位,方言有坑) |
| C 准确度/深度 | **40%** | **8** | 6.5 | RI(同名误连 0 条 vs cb 实锤 1 例;表链路/HTTP 全路径/接口→Impl 传导独有;但 throws 解析输 cb) |
| D 易用性 | 15% | 7 | **7.5** | cb(零配置上手;RI 要懂 schema,CLI impact 子命令损坏) |
| E 覆盖能力 | 10% | 6.5 | **9** | cb(Rust 实测可用+多语言+多项目管理;RI 无 Rust) |
| **总分(Java 深栈定位)** | | **7.4** | 6.6 | **RI** |

一句话:**cb 是"广而全"的通用代码图,RI 是"深而纯"的 Java 栈语义引擎**。RI 的护城河在
数据链路(MyBatis→表)、HTTP 全路径端点、接口→实现调用传导、以及歧义拒边带来的纯净 calls 图;
cb 的护城河在语言广度、零配置上手、get_architecture 一键全局体检、以及连续置信分(保留歧义供人裁决)。

## 1. 索引与数据规模

| 项 | RI v0.1.36 | cb |
|---|---|---|
| 全量索引时长 | **10.86s**(790 文件;其中 embedding 9.35s 占 86%,parse+resolve 仅 ~1.5s) | 无法测(MCP 调用无计时段);单命令单参数完成 |
| 产物大小 | 43MB(sqlite,裸 SQL 可查) | 项目条目 size_bytes≈35MB(内部格式,不完全可比) |
| 增量索引 | 内容级检测:touch 不改内容 → 790 文件全 unchanged,重扫 **0.60s** | git base_sha + detect_changes(定性:机制存在,本次未触发实测) |
| 实体 / 边 | 7,429 / 15,275(全为语义实体) | 11,535 / 32,957(含 DEFINES/CONTAINS_FILE/Folder 等结构容器边 ~13,600;语义边约 19,400) |

规模口径差异:cb 把 Variable(2563)/Field(2034)/File/Folder/Module 都建为节点,RI 只建语义实体
(method/field/class/interface/annotation/spring_bean/http_endpoint/mapper/table/column…)。
**RI 的图更"稠语义",cb 的图更"全符号"。**

## 2. 查询效率(B)

### B1 往返次数(以 Q1"反查 insertUser 调用者"为例)

- RI:`sqlite3` 1 条 SQL 直接出结果
- cb:`search_graph` 定位 → 发现短名歧义(Function/Method 双节点 × 接口/实现 3 份)→
  `qn_pattern` 再查 → `trace_path` 全限定名 → 返回空(见 C2)。
  **3-4 次往返**,其中两次被工具自身的数据形态坑了

### B2 响应字节数(token 成本)

| 查询 | RI | cb |
|---|---|---|
| 类级影响面 trace depth=2 | **80,331B**(紧凑视图,v0.1.36 实测) | trace_path 函数级 depth=2 ≈ 2.5KB/函数(18 callees,含全限定名) |
| 实体详情 | compact 档 `{id,kind,name,qualified_name,anchor}` | `qn_pattern` 单条命中即 ~3KB(fp/sp/bt 指纹全量下发) |
| 全局架构 | overview 工具(未测,待补) | get_architecture **巨响应**:聚类+分层+热点+完整 file_tree(含几十个空目录)≈15KB+ |
| 失控案例 | — | `labels(n)[0]` 聚合失效 → 原样返回 11,535 行 **260.9KB** |

RI 的紧凑视图 + 预算守卫(tools/list 22,837B / 预算 24,576B,有守卫测试防回涨)在 token
成本控制上是**有机制保证**的;cb 无预算机制,响应大小取决于查询写法,写错代价 260KB。

### B3 延迟

RI 全库聚合 SQL(聚类分布/置信分布/递归追表)均在亚秒级完成;cb 调用延迟无法在本环境测得(定性:体感流畅)。

### B4 表达力与方言

- RI:SQLite 全量 SQL(WITH RECURSIVE、json_extract、聚合、offset)无限制;代价是要了解 schema
- cb:Cypher 子集,实测限制:`type(r)`/`labels(n)[0]` 聚合失效、无 offset、`name_pattern`
  只匹配短 name(qn_pattern 才匹配全名)、`r.confidence` 聚合反而可用(行为不一致)
- cb 的错误 hint 质量好(trace_path 失败会给出可复制的 search_graph 查询),值得 RI 借鉴

## 3. 准确度 / 分析深度(C)

### C1 calls 边:两种哲学 + 一例实锤误连

| | RI | cb |
|---|---|---|
| 置信体系 | 离散:0.7 静态解析 ×2973,0.5 裸名注入 ×28 | 连续:0.03~0.95,共 22 档;<0.4 的约 **3,000+ 条** |
| 歧义处理 | A+ 防护:跨包同名拒边(本次 ambiguous_skipped=10,计入 metadata) | `candidates` 属性保留歧义,低分边照建 |
| 总量 | 3,001 条(纯) | 5,670 条(杂) |
| **误连实锤** | — | `SysUserServiceImpl.insertUser` 的 outbound trace 含 **`EsCrudController.insert`**(ruoyi-demo 的 ES 控制器,跨模块同名误连)且 trace_path 默认不过滤低分边 |
| 同位对照 | RI 全图查 EsCrud 误连 = **0 条** | — |

RI 代价:总量少(cb 5,670 vs RI 3,001),静态工具调用(如 `LoginHelper.getUserId()`)部分未收录
—— **cb 查全率占优,RI 查准率占优**。trace/impact 类下游任务吃纯度,RI 的取舍更对路。

### C2 跨层链路

- 两侧调用边都停在接口(Controller→`ISysUserService.insertUser`),但 **RI 显式建了
  `ISysUserService#insertUser —calls→ SysUserServiceImpl#insertUser` 传导边**(v0.1.23 静态解析),
  SQL 一跳拼全;cb 的 trace_path 从 Impl 出发 inbound = 空死路,agent 须自己想到去查接口节点
- cb 侧亮点:`SysUserController.add → ISysUserService.insertUser`(0.85 / field_type_hint)——
  字段类型提示解析质量好

### C3 数据链路(MyBatis→表)—— RI 独有

- RI:`table 31 / reads_table 47 / binds_to_statement 2 / column 422 / reads_column 152`;
  **Q2 实测**:从 SysUserServiceImpl 类递归(calls/injects/declares/mapped_from/reads_table/implements)
  一步抵达 `sys_user / sys_role / sys_post / sys_dept / sys_user_role` 5 张表
- cb:识别了 14 个 SQL 文件但**没有任何表/列实体**,该链路不可表达
- 这是 RI 相对 cb 最大的差异化能力,DB 变更影响分析(cb 完全做不了)

### C4 HTTP 链路

- RI:`http_endpoint` 243 个,**类级+方法级路径已拼好**(`GET /system/user/list` 直接可查),
  evidence confidence=1.0 指向 `@GetMapping("/list")` 注解行
- cb:Route 163 个但 `key_path` 只有方法级(`/list`),**类级 @RequestMapping 未拼接**——
  查 `/system/user` 的 Route = 0 条,agent 须手动两跳拼 URL;HANDLES 边 273 条(Route→Controller
  方法)质量好,但 get_architecture 展示层 `handler:""` 全空(自相矛盾的展示缺陷)

### C5 复杂度属性:同名属性,不同口径,数值不可互信

| 方法 | RI cx | cb cx | RI tld | cb tld |
|---|---|---|---|---|
| buildDataFilter | 17 | 14 | 2 | **5** |
| spelSmartSplit | 22 | 12 | 1 | 1 |
| finish | 18 | 13 | 1 | 2 |
| afterSheetCreate | 16 | 13 | 4 | 5 |
| getBackTaskNode | 16 | 11 | 5 | 5 |

系统性偏差:RI 的 cyclomatic 普遍高于 cb(条件/短路计数口径不同);top10 名单只有 4 个方法重合
(RI 榜首 `setColumnFeatureContext` 31 / `initColumnField` 29 在 cb 缺席,cb 榜上 `createWriterBuilder`
12 在 RI 榜外)。**结论:两工具的 complexity 各自内部自洽即可,跨工具数值没有可比性;
hotspot 定性结论(哪些方法复杂)大体一致,排序细节不同。**

### C6 架构聚类

- RI label propagation:582 簇;抽样:cluster 42 = 97% ruoyi-common-mybatis(高纯),
  cluster 4 = 62% workflow,cluster 2 = workflow+demo 混合
- cb Leiden:12 个大簇(87~269 成员)+ 自动 label + cohesion 分(0.43~0.75),同样近似按模块聚但有跨界
- **质量大体相当**;cb 的优势是自动标注(label/cohesion/top_nodes)开箱即读,
  RI 需要手写 SQL 做"簇→模块"归属分析(本次即是)

### C7 异常流与 tests —— cb 反超的一格

- **throws:cb 96 条全指向项目内异常类(ServiceException/UserException);RI = 0 条**。
  ruoyi 业务代码大量 `throw new ServiceException(...)`,CLAUDE.md 中"ruoyi 只 catch JDK 异常所以为 0"
  的解释不成立——RI 疑似只解析方法签名 `throws` 声明、不解析 `throw` 语句。**这是 RI 的真实缺陷与改进点**
- tests:RI 1 条 vs cb 5 条(项目本身测试少,双方都弱,判平)

### C8 检索

- cb:BM25 词法检索质量好(需 query 词与代码标识符重合);`semantic_query` 参数在当前索引下
  **静默退化为 bm25**(需要 moderate/full 重索引,行为不透明)
- RI:本地 embedding(scan 内置,7,050 实体 9.35s);英文 query 表现优秀——
  "user login authentication" 命中 `POST /auth/login`(0.53)/LoginHelper/AuthController/LoginBody/
  `sys_login_info` 表,跨 kind 端到端;**中文 query("用户登录认证")召回失败**(0.23 分命中 AlipayBillTask)
  —— embedding 跨语言能力是短板,建议报告用户后实测换多语模型

## 7. RI 改进建议(按本评测直接导出,按性价比排序)

> **v0.1.37 实施前探索修正了三条前提**(原始建议保留,修正注记如下):
> - 建议③ impact CLI **并非损坏**:`--request` 设计上就要求 ChangeRequest JSON(README 有示例),
>   评测时误传 Java 文件路径才报 JSON 错。真实缺陷是 UX(无裸实体名入口、报错不友好)与
>   `[analysis]` 配置未传入 ImpactAnalyzer(with_config 缺失)。
> - 建议⑤ "静态工具调用未收录"**部分误判**:`LoginHelper#getUserId` 实测已有 29 条 inbound
>   calls 边(static 类共 1273 条);真实缺口按量为 chain(1982→59)、qualified FQCN(230→11)、
>   继承静态方法(type_methods 不上溯 SuperclassOf)、外部库(结构性不可解)。
> - 建议⑥ embedding 开关(`[index] embedding`)与实体级 text_hash 缓存**均已存在**,
>   剩余可做的是耗时上收摘要与惰性构造。

1. **解析 `throw new XxxException(...)` 语句建 throws 边**(ruoyi 可立增 ~96+ 条,cb 已验证该图可行)——C7 唯一硬伤。
   *实施时发现更深一层:原 `throws_clause` 分支的节点 kind 写错(tree-sitter-java 里是 `throws`),
   签名 throws 收集从未工作过,一并未修*
2. **中文 embedding**:换多语模型或建中英词表映射,C8 中文 query 当前不可用
3. ~~修复 CLI `impact` 子命令~~ → impact CLI UX(--entity 快捷入口 + 友好报错)+ with_config 注入
4. **聚类自动标注**:给大簇生成 label/主导模块/cohesion,对标 cb 开箱即读
5. **补充静态调用解析**(qualified 截末段 + 继承上溯,chain 本期不做——误连风险与纯度定位冲突)
6. embedding 耗时上收 scan 摘要(embedding_ms/embedded_count)
