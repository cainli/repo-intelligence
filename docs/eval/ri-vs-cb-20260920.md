## 4. 新维度:性能 / 资源 / 增量(本轮增量核心,前四轮未测)

### 4.1 索引性能(ruoyi 790 java 文件,release 二进制,同机)

| 场景 | 耗时 | 说明 |
|---|---|---|
| 全量冷索引 | **19.85s** | 其中 embedding ~20s 为大头(多语 12 层推理);急用可 `[index] embedding=false` |
| 增量(零变更) | **0.43s**(46×) | 790 unchanged;edges 3929 + clusters 582 每次重建仅 0.43s |
| 增量(单文件变更) | **1.04s**(19×) | 仅重提该文件 34 实体 + 34 向量(embedding 625ms),789 unchanged |
| mtime 抖动(touch) | **不触发重提** | file_state 按**内容哈希**判定,mtime 变化零成本跳过 |

cb 侧无内容级增量索引的显式 API(index_repository 重建语义 + base_sha 记录),本轮未测得对应值——增量语义本身是 RI 独有供给。

### 4.2 查询延迟(CLI 冷启动含进程启动,3 次取最小)

`search` **0.01s** / `hotspots` **0.03s** / 递归追表 SQL(sqlite3 直查)**0.01s** / `semantic-search` **0.54s**(含 165MB 量化模型加载 + 中文 query 推理,输出正确)。结构化查询全部 ≤30ms,sqlite 直连无服务层开销。

### 4.3 存储构成

| 库 | RI | 其中 embedding | RI 纯图存储 | cb |
|---|---|---|---|---|
| ruoyi | 44M | 10.4M(7091×384 维) | **33.6M** | 41.6M |
| plus-ui | 19M | 5.7M(3876×384 维) | 13.3M | 5.5M |

ruoyi 侧 RI 纯图部分**小于** cb;plus-ui 侧大 2.4×,为 FTS 索引 + 顶层行号冗余列 + file_state 等固定开销在小库上的占比放大,非结构性膨胀。RI 库另含 cb 没有的向量、FTS、cluster_info 三类派生数据。

### 4.4 查询表达力

- RI:库是普通 sqlite,`WITH RECURSIVE`、任意聚合、JOIN、外部 BI 工具直连全部可用(本文所有验收 SQL 即证明)
- cb:Cypher 子集,`ORDER BY` **属性引用写法静默不排序**——本轮铁证:`ORDER BY f.complexity DESC LIMIT 6` 返回 6 行**全部 cx=0**(正确应为 6/5/4/...),无任何报错;别名写法(`ORDER BY cx`)才生效,而工具文档示例用的正是失效写法
